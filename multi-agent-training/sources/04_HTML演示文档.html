为什么需要多Agent？

Why Multi-Agent?
一个关键问题：既然普通的函数分工也能拆分任务，为什么还需要多Agent？核心区别在于——每个Agent拥有独立的LLM推理上下文和决策自主性。

函数分工 vs 多Agent

函数分工的模式：主控函数调用函数A，再调用函数B，再调用函数C。每个函数只是被动执行，没有自主决策能力，也无法根据中间结果调整策略。

多Agent模式则完全不同：每个Agent都拥有独立的LLM推理上下文，可以自主判断该怎么做。Agent A自己推理决策，Agent B也自己推理决策，它们可以根据实际情况动态协作。

三大优势

🧠

独立推理

每个Agent可以独立推理和决策，不需要主控函数预设所有分支。

🔄

动态协作

Agent之间可以根据实际情况动态协作，而非按固定流程执行。

🎯

上下文聚焦

单个Agent的Prompt更聚焦，推理质量更高，上下文窗口不被无关信息挤占。

典型场景

  • 复杂任务需要多个专业角色协作（产品经理、架构师、开发、测试）
  • 任务流程无法预先确定，需要Agent自主判断下一步
  • 需要并行处理独立子任务以提高效率
  • 单Agent的上下文窗口不足以承载所有信息

👔

Supervisor · 层级调度

中央调度Agent分配任务，Sub-Agent执行后汇报。适合动态任务分发、客服分流。

🏢

Hierarchical · 多层层级

多层嵌套的Supervisor结构（Supervisor-of-Supervisors）。适合大规模复杂系统。

🐝

Swarm · 群体协作

Agent之间自主交接控制权（Handoff），无中央调度。适合灵活协作、多角度讨论。

🔗

Sequential Chain · 顺序流水线

固定顺序的流水线，Agent依次处理。适合内容创作、数据处理。

🌐

Network · 对等网络

全连接对等网络，Agent可自由路由。适合高自由度探索型任务。

Supervisor：层级调度

Supervisor Pattern
Supervisor模式最直观——就像公司里的项目经理。Supervisor负责分配任务，Sub-Agent执行后汇报结果。有明确的上下级关系。

架构示意

Supervisor
任务分配 & 结果整合
Researcher
搜索工具
Analyst
分析工具
Writer
写作工具

代码实现

python
from langgraph_supervisor import create_supervisor
from langgraph.prebuilt import create_react_agent

researcher = create_react_agent(
    model, tools=[search_tool], name="researcher",
    prompt="你是一个Researcher，负责搜集和验证信息。"
)
analyst = create_react_agent(
    model, tools=[analyze_tool], name="analyst",
    prompt="你是一个Analyst，负责数据分析和洞察。"
)
writer = create_react_agent(
    model, tools=[write_tool], name="writer",
    prompt="你是一个Writer，负责内容创作和报告撰写。"
)
supervisor = create_supervisor(
    model=model,
    agents=[researcher, analyst, writer],
    prompt="""你是一个Supervisor，负责将任务分配给合适的Worker并整合结果。
    可用的Worker：
    - researcher: 负责搜集信息
    - analyst: 负责数据分析
    - writer: 负责内容创作"""
).compile()
result = supervisor.invoke({
    "messages": [{"role": "user", "content": "分析AI Agent市场趋势并撰写报告"}]
})
🔑 关键点
create_supervisor 接收 model、agents 列表和 prompt。prompt 里要明确告诉 Supervisor 有哪些 Worker 可用，各自的职责是什么。

# 中层Supervisor
tech_supervisor = create_supervisor(
    model=model, agents=[frontend, backend],
    prompt="你是技术团队负责人，协调前端和后端开发。"

🔑 嵌套的关键

Swarm：群体协作

Swarm Pattern
Swarm模式和Supervisor完全不同——没有老板，所有Agent地位平等。它们通过Handoff机制自主交接控制权。就像接力赛：Researcher跑完自己的部分，把接力棒交给Critic。

架构示意

Researcher
→ handoff_to_critic
⇄
Critic
→ handoff_to_writer/researcher
⇄
Writer
→ handoff_to_researcher

代码实现（LangGraph Swarm）

python
from langgraph_swarm import create_swarm, create_handoff_tool

# 定义Handoff工具——允许Agent之间交接控制权
handoff_to_critic = create_handoff_tool(
    agent_name="Critic",
    description="将控制权交接给Critic，请其评价和改进方案"
)
researcher = create_react_agent(
    model, tools=[search_tool, handoff_to_critic],
    name="Researcher",
    prompt="完成研究后，将控制权交接给Critic。"
)
swarm = create_swarm(
    [researcher, critic, writer],
    default_active_agent="Researcher"
).compile()

AutoGen实现对比

python
from autogen_agentchat.teams import RoundRobinGroupChat
team = RoundRobinGroupChat([researcher, critic, writer], max_turns=6)
⚠️ 注意
AutoGen 的 RoundRobinGroupChat 是轮询式讨论，与 LangGraph Swarm 的自主交接机制有本质区别。Swarm 是 Agent 自主决定交接，RoundRobin 是按固定顺序轮流发言。如需真正的 Swarm 行为，应使用 SelectorGroupChat。

Sequential Chain：顺序流水线

Sequential Chain Pattern
Sequential Chain最简单——固定顺序的流水线。每个Agent负责一个阶段，处理完传给下一个。适合步骤明确的任务。

架构示意

Research
→
Outline
→
Draft
→
Editor
→
SEO

代码实现

python
from langgraph.graph import StateGraph, START, END

class ContentState(TypedDict):
    topic: str
    sources: str
    outline: str
    draft: str
    final_content: str
    seo_content: str

graph = StateGraph(ContentState)
graph.add_node("research", research_node)
graph.add_node("outline", outline_node)
# ... 其他节点
# 定义顺序边——一条直线走到底
graph.add_edge(START, "research")
graph.add_edge("research", "outline")
graph.add_edge("outline", "draft")
graph.add_edge("draft", "editor")
graph.add_edge("editor", "seo")
graph.add_edge("seo", END)
🔑 关键
用 add_edge 定义固定的执行顺序。没有条件分支，没有动态路由，就是一条直线走到底。

Network：对等网络

Network Pattern
Network模式最自由——Agent之间全连接，可以自由路由到任意其他Agent。没有固定的调度者，也没有固定的流程。实现方式是加一个路由节点，由LLM决定下一步交给谁。

架构示意

Planner
⇄
Router
LLM决策路由
⇄
Executor
Reviewer

代码实现

python
# 路由函数：由LLM决定下一个Agent
def router_node(state: NetworkState) -> dict:
    result = model.invoke([
        HumanMessage(content=f"根据对话决定下一个Agent：planner/executor/reviewer/END")
    ])
    choice = result.content.strip().lower()
    if choice == "end":
        return {"next_agent": "END"}
    return {"next_agent": choice}

# 条件路由
graph.add_conditional_edges("router", route_decision, {
    "planner": "planner",
    "executor": "executor",
    "reviewer": "reviewer",
    "END": END,
})
💡 生产建议
路由函数依赖 LLM 返回精确的 Agent 名称，实际生产中建议使用结构化输出（with_structured_output）确保路由可靠性，避免 LLM 返回格式不一致导致路由失败。

把前面学的知识串起来，做一个完整的实战案例——用Supervisor模式搭建一个智能软件开发团队。这个案例有两个关键特性：重试限制和人工审批断点。

Architect

⏸️ 人工审批断点

代码实现

python
MAX_RETRIES = 3
supervisor = create_supervisor(
    model=model,
    agents=[pm, architect, frontend, backend, reviewer, tester],
    prompt=f"""按以下顺序调度：
    1. pm分析需求 → 2. architect设计系统 → 3. 开发 →
    4. reviewer审查 → 5. tester测试
    如果审查或测试不通过，最多重试{MAX_RETRIES}次。"""
).compile(
    checkpointer=InMemorySaver(),
    interrupt_after=["reviewer"]
)
result = supervisor.invoke(
    {"messages": [...]},
    config={"configurable": {"thread_id": "dev-1"}}
)
result = supervisor.invoke(
    None,
    config={"configurable": {"thread_id": "dev-1"}}
)
🔑 两个关键特性
重试限制：Supervisor 的 prompt 中指定最多重试 3 次，避免无限循环。
人工审批断点：interrupt_after=["reviewer"] 让 reviewer 完成后暂停，等待人类确认。这是生产级系统的必备机制。

通信协议：A2A与MCP

Communication Protocols
A2A管Agent之间怎么对话，MCP管Agent怎么用工具。一个是横向协作层，一个是纵向工具层，两者互补，不是竞争关系。
🤝

A2A · Agent-to-Agent

Google发布的开放协议，解决不同框架/厂商Agent之间的互操作问题。已有150+组织参与，发布v1.0稳定版。

🔧

MCP · Model Context Protocol

Anthropic发布的开放协议，标准化Agent与外部工具/数据源的连接。架构：Host ↔ Client ↔ Server。

A2A核心概念

概念说明
Agent CardAgent的"名片"，JSON格式，发布在 /.well-known/agent.json，描述能力、端点、认证方式
Task交互的基本单元，生命周期：submitted → working → completed/failed
MessageAgent间交互的标准化信封，基于JSON-RPC 2.0
v1.0特性Signed Agent Cards（密码学签名验证Agent身份）

MCP三种能力

能力说明示例
ToolsAgent可调用的函数/工具数据库查询、API调用
ResourcesAgent可读取的数据/文件配置文件、日志
Prompts预定义的提示词模板代码审查模板
💡 一句话总结
A2A = Agent ↔ Agent（横向协作层），MCP = Agent ↔ Tool（纵向工具层），两者互补，不是竞争关系。

多Agent安全

Multi-Agent Security
多Agent的安全问题是首要障碍，不是普通挑战。Agent链的传播效应会放大单点安全问题——一个Agent被注入恶意指令，可能通过Handoff传播到整个系统。

五大威胁

威胁类型描述防护措施
Prompt Injection传播恶意输入通过Agent链放大传播输入验证、消息签名、上下文隔离
Agent身份伪造伪造Agent身份获取未授权访问A2A Signed Agent Card
数据泄漏Agent将敏感数据传递给不可信Agent数据分级、输出过滤、审计日志
资源耗尽Agent循环调用耗尽Token和计算资源Token预算、调用深度限制
权限越界Agent获取超出授权的工具/数据访问最小权限原则、工具白名单

安全防护三原则

🛡️

结构化消息

拒绝纯文本，强制Agent间传递结构化数据，防止注入攻击。

🔐

工具白名单

每个Agent只能使用授权的工具，遵循最小权限原则。

💰

Token预算

设置Token预算和调用深度限制，防止Agent循环调用耗尽资源。

防护代码示例

python
class SecureAgentCommunicator:
    def validate_message(self, message: AgentMessage) -> AgentMessage:
        # 1. 验证消息格式（拒绝纯文本，强制结构化）
        if not isinstance(message.content, dict):
            raise SecurityError("消息内容必须为结构化数据")
        # 2. 验证工具调用权限
        if message.message_type == "task":
            tools = message.content.get("tools", [])
            allowed = self.allowed_tools.get(message.receiver, [])
            for tool in tools:
                if tool not in allowed:
                    raise SecurityError(f"无权使用工具: {tool}")
        return message

关键挑战与决策矩阵

Challenges & Decision Matrix
不要为了多Agent而多Agent。多Agent的Token开销通常是单Agent的2到5倍，必须通过决策矩阵来判断到底值不值得。

三大工程挑战

挑战1：通信开销 ▼

多个Agent之间需要频繁通信，每次通信都可能触发LLM调用。通信开销应控制在总Token的30%以内。

解决：使用结构化消息，减少不必要的LLM调用。LangGraph的做法是Sub-Agent的输出直接作为消息传递，Supervisor只在需要决策时调用LLM。

挑战2：死锁和循环依赖 ▼

两个Agent互相等待，形成死锁。

解决：设置超时和递归深度限制。调用链深度不应超过10层。

挑战3：结果冲突 ▼

不同Agent给出不同的答案，需要仲裁。

解决：投票或仲裁机制。加权投票按置信度汇总，专家仲裁由指定Agent做最终裁决。

何时使用多Agent：决策矩阵

常见问题

FAQ
Supervisor和Swarm该选哪个？ ▼
如果任务流程相对确定、需要集中调度，选Supervisor。如果需要多角度讨论、Agent之间需要灵活交接，选Swarm。简单来说：有老板选Supervisor，没老板选Swarm。
多Agent的Token开销怎么控制？ ▼
三个关键策略：1）使用结构化消息减少不必要的LLM调用；2）设置Token预算和调用深度限制；3）通信开销控制在总Token的30%以内。如果简单任务用单Agent就能完成，不要为了多Agent而多Agent。
A2A和MCP是什么关系？ ▼
互补关系，不是竞争关系。A2A解决Agent之间的互操作问题（横向协作层），MCP解决Agent与外部工具的连接问题（纵向工具层）。一个管Agent间对话，一个管Agent用工具。
Sequential Chain和普通Pipeline有什么区别？ ▼
关键区别在于每个节点是一个拥有独立LLM推理上下文的Agent，而不是一个简单的函数。这意味着每个阶段都可以自主推理和决策，而不是机械地执行预设逻辑。
如何防止Agent之间的Prompt Injection传播？ ▼
核心策略：1）强制Agent间传递结构化数据，拒绝纯文本；2）对输入进行验证和清洗；3）使用消息签名验证来源；4）上下文隔离，限制Agent可访问的信息范围。
Network模式的路由可靠性怎么保证？ ▼
路由函数依赖LLM返回精确的Agent名称，建议使用结构化输出（with_structured_output）确保路由可靠性。同时设置兜底机制：如果路由失败，默认回到Supervisor或结束。
