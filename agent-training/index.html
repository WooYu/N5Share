贯穿案例：订单分析助手

给你一份订单 CSV，回答：已完成订单的净销售额是多少？各品类表现如何？

字段业务含义
gross订单原金额
refund退款金额
statuscompleted / cancelled

验收条件

  • 只统计 completed
  • 净销售额 = gross − refund
  • 保留订单 ID，结论能够复算

数据为合成教学样本，金额单位：人民币。

最小控制循环

for step in range(MAX_STEPS):
    decision = agent.decide(goal, observations)
    if decision.is_final:
        return validate(decision.answer, evidence)

    call = validate_tool_call(decision.action)
    observation = tools.execute(call, timeout=30)
    observations.append(observation)

return stopped("预算耗尽，尚未完成")

常见失败与停止策略

现象应对动作结束条件
参数或字段不匹配返回 schema，修正请求持续无进展则停止
工具暂时不可用有限重试与退避达到重试或时间预算
相同动作反复出现检测重复，重新规划无法获得新证据
工具结果不足补充查询或请求信息说明缺失，避免编造

完成、失败、受控停止，是不同的状态。

有用的反思必须改变下一次行动

信息不足的反思

“这次失败了，下次认真一点。”

没有原因、证据或可执行修正。

可执行的反思

“把 sales 当成字段是未经验证的假设。下次依据 inspect 的实际字段，用 gross − refund 计算。”

检查反思质量：失败点 → 支持证据 → 修正动作 → 再次验收。

什么时候值得拆成多个 Agent？

拆分的理由

  • 知识、工具或权限边界不同
  • 子任务可独立交付与验收
  • 需要不同上下文或评价视角

需要付出的代价

  • 更多模型调用与上下文传递
  • 协调、重试与状态合并
  • 更难定位错误与控制延迟

先证明单 Agent 的瓶颈，再用多 Agent 解决具体问题。

Swarm：通过交接转移控制权

接待 Agent
→
领域 Agent
→
处理 Agent
handoff = 目标角色 + 当前任务 + 必要上下文 + 返回约定

适用场景

下一位专家随对话与任务状态变化，例如多领域服务。

设计重点

限制交接次数，定义状态归属，避免 A ↔ B 循环转交。

此处 Swarm 指协作模式；不等同于某个同名 SDK，也不表示必须全连接或并行。

共享状态：先定义谁能写什么

状态字段主要写入者合并或更新原则
plan / plan_version规划 Agent以新版本替换，保留事件历史
observations / artifacts执行运行时追加证据，避免覆盖其他任务
reflection memory规划 Agent记录反馈、修正与适用范围
status / verified调度器与校验器统一结束条件，校验后才完成

并发写入同一字段时，需要 reducer、版本检查或锁；聊天记录不替代状态模型。
