# Agent 选型与协作设计卡

课程共 41 页、90 分钟。先了解目标与路线，第 04 页起用“周末出游”理解七个能力阶段，再把选型方法用于远程专家辅助实战。出游演示可切换晴天/雨天和 300/200/100 元预算，“下一步演示”为离线固定样例；“真实模型演示”使用 CCSwitch 与官方 Codex CLI，工具仍读取合成资料，不查询实时天气或调用预订服务。

## AI 术语速查

| 英文 | 中文 | 本课中的含义 |
| --- | --- | --- |
| LLM · Large Language Model | 大语言模型 | 根据输入生成内容，可作为决策来源；本课用固定样例演示 |
| Agent | 智能体 | 围绕目标选择行动、使用工具并根据反馈继续或停止 |
| RAG · Retrieval-Augmented Generation | 检索增强生成 | 先找相关资料，再让回答参考这些资料 |
| Tool Calling | 工具调用 | 提交结构化请求，由程序校验并执行工具 |
| ReAct · Reasoning and Acting | 推理与行动交替 | Thought-Action-Observation 循环：判断、行动、观察，再决定下一步 |
| Plan-and-Execute | 规划与执行 | 先分解任务，再执行；必要时调整计划 |
| Reflexion | 反思 | 将反馈整理为经验，用于后续尝试；不等于训练模型权重 |
| Plan-and-Execute + Reflexion | 规划执行与反思闭环 | 先规划再执行，从失败反馈中修订计划，重新执行与验收 |
| Supervisor | 主管模式 | 集中分派与汇总，可作为层次化系统的一层 |
| Hierarchical | 层次化 | 总主管管理组长，组长再管理子角色 |
| Swarm | 动态交接协作 | 当前角色按需要交接任务与控制权，限制交接次数和出口 |
| Multi-Agent | 多智能体协作 | 多个角色分工、交换结果并共同完成任务 |
| Workflow | 工作流 | 按预设步骤和条件分支执行，可包含模型节点 |
| Human-in-the-loop | 人工介入 | 在关键环节由人补充、审核或接管 |

能力演进按 LLM → RAG → Tool Calling → ReAct → Plan-and-Execute → Reflexion → Multi-Agent 展开。这是讲解顺序，不是每个任务必须走完的升级路线；离线模式角色和决策均为模拟；真实模式使用独立模型调用生成决策，需按实际证据与验收结果评价。

真实模型课堂提示词与接入要求见[大模型演示指南](model-demo-guide.md)。本地服务已提供真实模型模式，直接打开 HTML 时保留离线示意。

## 先定义任务

- 输入是什么？输出交付给谁？成功条件能否检查？
- 哪些条件与工具映射可以穷举？哪些需要解释非结构化信息、探索未知路径？
- 可接受的时延、调用成本和失败处理方式是什么？

## 选择推理与协作方式

| 任务特征 | 优先考虑 | 需要付出的代价 |
| --- | --- | --- |
| 规则完整、结果确定 | 普通程序 | 规则变化时修改程序 |
| 步骤、分支条件和工具映射已知，含按证据补查 | 固定工作流；必要节点可用模型 | 节点输出校验、异常分支 |
| 路径难以穷举，需解释非结构化信息并选择工具 | 单 Agent / ReAct | 工具约束、循环预算、可观察性 |
| 多步骤、有依赖和全局验收 | 已知依赖用工作流；动态任务分解再评估规划执行 | 计划维护、重规划、状态管理 |
| 新增独立上下文、工具权限或专业责任归属 | 评估角色拆分；也可由普通服务落实 | 边界校验、独立产物与协作成本 |
| 拆分后需要统一分派与出口 | 主管协调 | 调度瓶颈、错误分工、通信成本 |
| 拆分后子任务可独立启动 | 并行分析 + 汇总 | 上下文同步、重复工作、证据冲突 |
| 独立专业审查，验收明确且结果可修订 | 提案—评审—修订 | 评审质量、修订上限、人工接管 |

“下一步依赖证据”不等于需要 Agent，已知条件分支仍是工作流。先验证普通代码或确定性工作流，再评估单 Agent，最后判断新增的上下文、权限或专业责任隔离是否值得拆分。非结构化字段提取也可以是工作流中的一个模型节点，不自动构成 Agent。多个角色可以使用同一个模型，多个函数不自动成为多个 Agent。

后半程“接单前资料初审与专家辅助”只核对 voltage、dtc、gateway 三类固定字段，并参考合成知识规则；缺电压补读、冲突查事件时间、失败转人工均有已知规则，`workflow` 足够。协作示例新增了敏感日志与资料上下文隔离、不同工具权限、独立专业审查责任的教学假设；实际角色决策仍为规则模拟，不声称已经实现生产权限系统。

运行台“基线与三种模式”在同一情景、来源、预算和验收下比较 `workflow / supervisor / parallel / review`；`integrated` 用于组合案例。五种模式共用合成记录和轨迹结构，五种情景共 25 份预录轨迹，与前半程七个出游演示分开。先比较结束状态、证据与调用量，再讨论耗时，不能从规则轨迹推出多 Agent 模型质量提升。

`workflow` 补读是预设条件分支：计划保持 v1、修订轮次为 0、无 Revision/Dispatch；不能把每次补充读取都记成计划修订。

## 选择实现框架

先分三层：ReAct、规划与反思是推理策略；Supervisor、层次化与 Swarm 是协作组织方式，并行与评审可与其组合；AutoGen、MetaGPT、LangGraph 是开发框架。三层分别选，不能把 ReAct 与 LangGraph 当成二选一。

| 具体约束 | 框架候选与理由 | 仍需手写或核对 |
| --- | --- | --- |
| 本课要对比固定流、条件分支、并行汇合与回路 | LangGraph：显式 State / Node / Edge，控制与状态可观察 | 领域工具、状态 schema、路由、reducer、证据验收、预算、日志 |
| 已有消息团队，主要问题是对话交互与委派 | AutoGen：AgentChat 团队、Core 消息运行时 | 工具、终止、上下文边界；维护和迁移方案 |
| 专业角色遵循 SOP，交付物与验收归属清楚 | MetaGPT：Role / Action / Team | 业务 SOP、产物验收与依赖适配，不能直接套软件团队流程 |
| 等待用户上传、进程重启后恢复 | LangGraph 可提供检查点与中断机制；普通持久状态机也可用 | 存储、thread_id、恢复入口、鉴权、幂等和过期校验 |
| Java / 前端 / 客户端需要接入 | 先定 HTTP、DTO 与业务边界，再选运行时 | 按版本核对语言 SDK，不能假设各语言能力对等 |

本课选择 LangGraph 是为了可见的编排机制；原始固定字段任务用普通代码也可完成。框架不会替代业务规则或自动提供生产恢复。

维护信息核对于 2026-09-21：AutoGen 已进入 Maintenance Mode，无新功能或增强，由社区维护，官方推荐新用户评估 Microsoft Agent Framework；现有项目仍需自行评估支持和迁移。MetaGPT README 的 Python 范围为 ≥3.9 且 <3.12，需另查具体 release 与依赖；本课 Python 3.10+ 主 Demo 不与其混装。Python 示例不代表 Java、TypeScript 或 .NET SDK 能力对等。

## 画出最小协作系统

| 设计项 | 必须能回答的问题 |
| --- | --- |
| 目标与验收 | 怎样证明交付物完成任务？ |
| 角色 | 每个角色为什么独立？输入和输出分别是什么？ |
| 工具 | 谁能调用？参数、结果和失败分别怎样表示？ |
| 消息 | 携带哪个任务、哪些证据引用和什么状态？ |
| 共享状态 | 谁写入、怎样合并、怎样保留来源？ |
| 调度 | 谁决定下一步？并行结果什么时候汇合？ |
| 分歧处理 | 按什么证据取舍？无法消解时交给谁？ |
| 停止与人工介入 | 成功、预算耗尽、工具失败分别怎样结束？ |

## 业务和演示核对：接单前资料初审与专家辅助

业务背景仅采用[道通远程专家官方中文页](https://www.auteltech.cn/cloud/3942.jhtml)：连接在线专家和客户，提供远程诊断、编程、防盗、ADAS 与咨询；支持 VIN 信息、导入报告、发布订单、AI 智能匹配专家、多种沟通方式和实时服务/连接状态。页面未披露 LLM 或多 Agent 实现，“AI 智能匹配”不能证明使用本课架构。

课堂设定：门店报告通信故障 U0121 并请求远程专家咨询 → 接单前汇总电压、故障码、网关记录及知识资料 → 缺失则补充，冲突则核对事件时刻与采集时间 → 保留证据来源，提交专家人工复核。AI 初审及协作流程为教学设计，专业人员负责判断；固定记录、工具和诊断后端行为保持原样，不连接或操作真实车辆。

U0121 表示与 ABS 控制模块失去通信的故障码，不等于模块损坏；voltage 是供电电压；gateway 是通信网关。远程网络链路故障不能证明车辆故障，网关可达也不证明车辆正常。读数与规则均为合成教学材料。

`review / missing`：缺电压 E-VOLTAGE → 草稿评审退回 → 计划 Revision → `read_supplemental` 返回电压 → 重写草稿 → 重新审查通过。缺失的不是采集时间；补充不可得才转人工。报告通过仍待人工确认。

## 设计练习：等待客户端上传（尚未实现）

新增要求：工具中没有缺失资料，需要门店通过客户端上传。提交暂停/恢复图、一条上传消息与正常、重复、过期上传的验收条件。参考答案如下，也见培训 README 和讲稿；当前 Demo 没有上传接口或持久暂停恢复。

| 设计项 | 参考答案 |
| --- | --- |
| 角色 | 客户端展示请求并上传；Java 服务鉴权与校验；编排器保存和恢复；证据角色核验；审查者验收报告 |
| 暂停与保存 | 设置 waiting_client_upload，持久保存工单/运行、版本、证据、草稿、缺失项、预算、恢复节点、upload_request_id、到期时间；结束本次 HTTP 请求 |
| 消息 | client_evidence_uploaded 携带 case_id、run_id、upload_request_id、expected_plan_version、message_id、idempotency_key、evidence_refs；身份取自认证会话 |
| 恢复 | 校验权限、内容和版本，从待补充节点继续，保留有效证据与剩余预算，重新审查 |
| 重复 / 过期 | 唯一幂等键与原子状态转换使同一上传只恢复一次；旧请求、旧版本或已结束任务只留审计，不覆盖当前状态 |
| 异常与验收 | 重启可恢复；越权拒绝；取消后不再恢复；超时或无法补齐转人工；报告不等于人工批准 |

无需仅为上传增加一个 Agent。普通持久状态机可以实现；若使用 LangGraph，另配 checkpointer、thread_id、interrupt/resume，并验证恢复重放与外部副作用幂等。
