## P05 · 三个缺口，指向同一个工程问题

基线：单轮 LLM 卡在哪｜3 分钟｜核心 2 分钟

讲解：不要把缺口概括为“模型不够聪明”。一次生成无法自动获得最新天气，也不会天然遵循可靠的金额核算。工程上可以把缺口拆成四个工具：查天气、查场馆、算完整费用、核对预算。模型负责决定下一步需要什么信息，宿主程序负责真正执行。工具也可能失败，因此后面还需要停止条件和异常处理。

提问：若只把提示词改成“请仔细思考”，天气数据会自动出现吗？请同学区分更谨慎的措辞和新事实的获取。

演示操作：在纸上写“未知事实 → 工具请求 → 观察 → 下一步”，作为进入下一章的过渡。核心路线省略个人案例分享。

转场：ReAct 把这条短链做成可重复执行的循环。

## P06 · ReAct：根据新事实，决定下一步

ReAct 推理范式｜3 分钟｜核心页

讲解：ReAct 通常展开为 Reasoning and Acting。图里的 Thought 只指可公开展示的简短决策摘要，例如“先查天气以判断室内外”，不是模型私有的内部思维过程。Action 是模型提出的请求，宿主可以校验和拒绝。Observation 是执行结果，例如结构化的 rain；它成为下一轮的输入。循环不意味着无限次运行，退出条件属于宿主职责。

提问：如果模型写出“观察到雨”，但实际没有调用天气工具，这能算 Observation 吗？答案是否定的，事实需要可追溯来源。

演示操作：顺着 SVG 三个节点走一遍，用天气工具的例子口头代入。强调图上的回路是数据依赖，不是让模型反复自言自语。

转场：把三个节点展开，看看谁负责什么。

## P07 · 模型提请求，宿主执行并回填

ReAct 推理范式｜3 分钟｜核心页

讲解：把 Action 类比为客户端发给服务端的 DTO。模型可能选择未知工具、遗漏参数或给出不允许的类型，宿主必须验证。即使模型在 JSON 中附带所谓观察，也不能当作执行结果；只接受可信工具实际返回的数据。本课工具只读合成资料，没有购买、发消息等副作用。生产系统还要处理鉴权、幂等、超时和审计，这些不是一句提示词能保证的。

提问：在你熟悉的技术栈里，工具参数校验应该放在哪里？预期答案是服务端边界，而非只信任模型输出。

演示操作：指读请求 JSON，区分 tool 与 args。让学员口头补出 get_weather 返回结果的写入者：宿主程序。

转场：有了清晰边界，就能逐步检查整条任务轨迹。

## P10 · 三个常见失效点

ReAct 推理范式｜2 分钟｜核心页

讲解：重复调用不一定错误，例如工具结果过期后重新查询是合理的。要比较参数、状态变化和结果时效，而不是简单禁止同名工具二次出现。错误累积可能来自工具异常、错误解析或陈旧信息，应保留来源与错误类型。无限循环则属于控制问题：如果没有硬性预算，即使每一步单独看似合理，整个任务仍可能消耗失控。

提问：遇到工具超时，重试一次合理；重试到第十次还合理吗？让同学说出可执行的重试策略。

演示操作：回忆刚才演示最后的完成或无解事件，指出它是可观察的终态。无需额外运行。

转场：下一页把这些防线变成具体的结束条件。

## P11 · 什么时候必须停下来

ReAct 推理范式｜2 分钟｜核心页

讲解：先区别软性策略和硬性约束。模型可以建议停止，但宿主要独立维护额度并执行终态判定。本课真实模式上限是 12 次模型调用、20 次工具调用、8 分钟，任何一项超限都不能包装成完成。候选耗尽时输出已检查过哪些条件，说明调整预算或改变餐费等需要用户重新授权；不能擅自修改约束。取消同样必须阻止后续成功事件继续发布。

提问：“我找不到 100 元以内的方案”是不是有效结果？是有效的失败说明，但不是通过任务验收。

演示操作：指向终态三行，并让学员给每行各起一个状态名，例如 completed、stopped、needs_human。

转场：做一道题，判断什么时候真的需要这种逐步获取事实的机制。

## P12 · 判断：哪一步真的需要模型来选？

ReAct 推理范式｜2 分钟｜核心页

讲解：给二十秒独立选择，再请学员指出决定性条件。Android ANR 的竞争假设包括锁等待、主线程 I/O 和 Binder 阻塞；读取 trace 后才选择下一项针对性检查，目前没有可靠 runbook 能覆盖这些分支，因此适合有界 ReAct。其余任务即便输入尚未取得，动作和分支仍由已知规则决定，可以直接执行工具。若将来 ANR 的诊断路径也能稳定规则化，应把相应步骤收回普通工作流。Java 现场无现成 runbook、需结合新堆栈选择进一步诊断时，同样可以考虑 ReAct。

提问：如果有人把“先查日志、再查指标”写成固定脚本，这是否自动是 ReAct？不是。要说明哪一步由模型根据证据选择，以及选择空间和停止条件。

演示操作：点击选项后，要求学员补一句：我选择该项，因为下一检查动作取决于什么证据；其余项为什么无需模型决定流程。诊断中只允许读取经脱敏的日志与测量资料，不把猜测写成根因已证实。

转场：有些任务需要先把目标展开成依赖计划，再执行其中的检查。

判断题：以下哪项最需要模型按观察选择下一动作？

A. 前端发布按固定规则执行 lint、单测和构建，失败即停止
B. Java 告警按已验证 runbook 查询指标，再依固定阈值分流
C. Android 偶发 ANR 原因未明，需读 trace 判断接着查锁、I/O 还是 Binder
D. 读取天气与票价后，按已写好的过滤和预算规则选择场馆

答案：C。ANR 示例缺少可枚举的可靠诊断路径，需要解释观察再选检查动作。其他任务已有动作与分支规则，查询未知数据也可由确定性工作流完成。

## P13 · ReAct 的代价：每一步都重新决策

Plan-and-Execute + Reflexion｜2 分钟｜核心页

讲解：原设计用“随步数线性增长”表达成本趋势，但严格来说每轮上下文可能变长，输入 token 总量也可能增长更快，所以这里使用通常随回合增加的保守表述。Plan-and-Execute 的收益来自减少重复规划，不保证必然更便宜。计划越长、环境越不稳定，重新规划的代价越大，必须用实际延迟与调用数据验证。

提问：查天气、筛类型、计算费用这几步，哪些顺序可以提前固定，哪些需要观察以后再决定？

演示操作：在纸上写出一个五步任务，圈出真正需要模型判断的步骤。

转场：先看拆分后的控制结构。

## P14 · 先给全局计划，再按计划执行

Plan-and-Execute + Reflexion｜3 分钟｜核心页

讲解：Planner 不只是列一个漂亮清单，而是说明依赖、动作和完成条件。Executor 可以是确定性程序，也可以是受约束的 Agent，两者不是同义词。稳定步骤可以批量执行，但有数据依赖的动作不能盲目并行。本例执行器不拥有任意改写目标和验收标准的权力，遇到无法完成的步骤就返回结构化偏差。

提问：如果第二步依赖第一步的天气结果，能为了加速同时执行吗？可以提前查全部资料，但不能在未知天气时宣称选型已通过。

演示操作：沿图走一遍正常路径，再走一次失败回路。提醒学员接下来先观察一份计划，不急于替它修正。

转场：这份 v1 看起来完整，费用项也没有缺失。

## P16 · 执行计划 v1

Plan-and-Execute + Reflexion｜4 分钟｜核心页

讲解：单步执行时，先展示植物园被选中、完整费用 270 元和预算通过，再停在最后的可行性检查。让学员看到雨天观察到达之后户外场馆失效。对于雨天 300 元这一固定场景，缺少天气前置是唯一预设根因。若改为 200 或 100 元，270 元会同时触发预算问题，此时不能继续说只有一个失败原因；变更条件后要重新诊断。

提问：270 元没有超预算，为什么仍不能输出行程？因为总预算只是验收条件之一，天气兼容同样必须满足。

演示操作：设置雨/300并重置。先单步到费用和预算结果，再执行天气校验。回看选择场馆时的状态，确认当时 weather 尚未知。可切晴/300对照正常结果；低预算留作课后探索。

转场：失败信息告诉我们，问题出在计划结构。

## P17 · 执行失败：顺序错了，工具并没有坏

Plan-and-Execute + Reflexion｜2 分钟｜核心页

讲解：区分三类失败：工具调用失败、工具正确返回不利事实、计划根本没有遵守依赖关系。本例是后两者相结合：天气工具正常返回 rain，暴露了先选场馆的结构问题。重复调用天气不会让雨消失；只把“出行程”步骤重试也无助于解决问题。固定默认场景是为了让学员清楚看到一种可修复的根因。

提问：把执行重试三次，结果会变好吗？不会，需要改变的是前置依赖，不是重试次数。

演示操作：指向“先选 → 后查”的顺序，画一条反向依赖箭头。无需重跑。

转场：Reflexion 用失败证据指导下一版计划。

## P18 · Reflexion：让反思产出一个可执行修正

Plan-and-Execute + Reflexion｜3 分钟｜核心页

讲解：Reflexion 是利用失败反馈形成可复用修正的思路，不是给模型加一段道歉。反思记录至少包含证据、原因和可验证的改动。本课只在单次运行中保存计划版本与反馈，没有实现跨会话长期记忆。也不保证模型一次反思就找对原因，因此修订后必须再次走工具与验收链，不能把自信的总结当作证明。

提问：下面哪句话可检验：“我会更认真”和“在选择场馆前调用天气工具”？请同学再提出一个执行后能验证的修正规则。

演示操作：顺着图读出四个阶段，强调修订之后是重新执行，回路不直接通向成功。

转场：把可执行结论落实到 v2 的具体步骤。

## P33 · LangGraph：写出节点、分支，再读状态更新

框架概览与选型｜3 分钟｜核心 2 分钟

讲解：从入口讲起：release_input 是共同资料，ReleaseState 声明 source、reports、result；collect_findings 调用 collect_reports 读取事实并产出报告；release_route 用宿主 evaluate 规则选边，不让模型用一句“可以发布”直接决定终态。add_conditional_edges 明确三条分支：有阻断项进入 block，单纯缺证据进入 missing，证据齐备且无阻断项进入 allow。allow 分支输出 READY_FOR_MANUAL_REVIEW，仍不自动部署。stream_mode=updates 能观察每个节点返回的状态更新，不能理解成工具内部的全部日志。完整导入与辅助函数在手册中。默认教学回放确认接线，真实模型仍需证据校验。当前 compile() 没配置检查点，不能据此声称已有持久恢复。API 官方核对日期为 2026-09-23，实际执行证据以手册记录为准。

## P50 · 工程实操：补一条消息，或一个失败出口

收尾｜3 分钟｜核心 2 分钟

讲解：课堂三分钟只练局部：三十秒读输入，六十秒选一项补消息或失败出口，六十秒同伴说明，三十秒打开参考答案核对。核心路线两分钟为二十秒读题、五十秒补写、五十秒核对。不要把这一次短练习计作已经独立完成整个系统设计。故障一应拒收旧提交证据并补当前候选的缺失检查；故障二应保存并复用 run_id，页面重新观察同一任务，界面重建本身不触发服务端任务取消；故障三由宿主维护不可倒退的终态，迟到响应不能覆盖已确认取消。Android 应同时绑定 commit_sha、artifact_sha256、build_variant 和设备/API 环境；同提交的 debug 与 release 性能报告不能直接互用。配置变更可通过 ViewModel 保留观察入口，进程恢复还需按需求保存任务标识；停止收集 Flow 不等于取消远端任务。课后完整十分钟练习：两分钟写选型理由与验收；两分钟补角色、权限和一次交接消息；两分钟列共享字段、写入者及证据版本；两分钟推演三个故障与资源上限；两分钟对照参考契约评分并补缺口。允许用确定性工作流或单 Agent，只要解释充分。任务状态与发布建议分开：检查已完成但发现阻断项，可写 COMPLETED + BLOCK；缺证据、执行失败、超限和取消均不能伪装成可发布。

提问：目标仍为 B，能否把 A 的“测试全过”当作 B 的证据？页面旋转时，取消的是界面观察还是服务端任务？请任选一项写成宿主能执行的规则。
